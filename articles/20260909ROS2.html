对ROS2基础知识的简要理解

尽量通俗易懂

#笔记#ros2

ROS 2 核心概念与基础知识

工作空间 Workspace

工作空间是 ROS 2 项目的顶层开发目录，用于统一存放、编译和管理多个功能包。

典型目录结构如下： 

ros2_ws/
├── src/
├── build/
├── install/
└── log/

src 用于存放功能包源码。 build 用于保存编译过程中的中间文件。 install 用于保存编译后的可执行程序、库和资源。 log 用于保存编译日志。

工作空间通常使用 colcon 进行统一编译： 

cd ~/ros2_ws
colcon build

编译完成后需要加载当前工作空间环境： 

source install/setup.bash

该命令的作用是将当前工作空间中的功能包、可执行程序、库和资源加入当前终端的 ROS 2 环境，使 ros2 run、ros2 launch 等命令能够找到刚编译的内容。

实际项目中，一个机器人通常使用一个主要工作空间，在 src 中放置驱动、导航、描述、接口、启动等多个功能包。

功能包 Package

功能包是 ROS 2 中组织代码和资源的基本单位。

不同功能通常拆分到不同功能包中，例如： 

robot_driver
robot_navigation
robot_description
robot_interfaces
robot_bringup
robot_simulation

一个功能包可以包含一个节点、多个节点，也可以完全不包含节点。

例如 robot_description 功能包通常主要保存 URDF、Xacro、Mesh 和 RViz 配置，不一定包含可执行节点。

功能包中的 package.xml 用于描述功能包名称、版本、维护者以及依赖关系。 

<depend>rclcpp</depend>
<depend>geometry_msgs</depend>

上述内容表示当前功能包依赖 rclcpp 和 geometry_msgs。

C++ 功能包通常还包含 CMakeLists.txt，用于描述编译规则。 Python 功能包通常通过 setup.py 或 pyproject 等方式描述安装和入口信息。

节点 Node

节点是 ROS 2 中执行具体功能的运行单元。

一个节点通常负责一个相对明确的功能，例如： 

lidar_node
camera_node
base_node
localization_node
planner_node
controller_node

节点可以创建 Publisher、Subscriber、Service、Client、Action Server、Action Client 和 Parameter。

节点是 ROS 2 通信图中的基本参与者。

常用查看命令： 

ros2 node list

用于查看当前 ROS 2 系统中存在的节点。 

ros2 node info /node_name

用于查看某个节点发布的话题、订阅的话题、提供的服务以及使用的动作接口。

阅读节点源码时，应优先关注节点的输入、输出和配置，而不是立即分析内部所有算法代码。

话题 Topic

Topic 是 ROS 2 中基于发布订阅模型的异步通信机制。

Publisher 向某个 Topic 发布消息，Subscriber 订阅该 Topic 并接收消息。 

Publisher
    │
    ↓
  Topic
    │
    ├── Subscriber
    ├── Subscriber
    └── Subscriber

Publisher 和 Subscriber 不需要直接知道彼此的信息，只需要保证 Topic 名称、消息类型和 QoS 能够匹配。

Topic 主要用于持续产生的数据，例如： 

/scan
/camera/image_raw
/odom
/cmd_vel
/imu/data

典型使用场景包括激光雷达、摄像头、IMU、里程计、速度控制、机器人状态等。

创建 Publisher 时应重点关注三个信息： 消息类型、Topic 名称和 QoS。

创建 Subscriber 时应重点关注： 订阅的话题、消息类型以及收到消息后执行的回调函数。

Topic 是异步通信机制，发布者通常不会等待订阅者返回结果。

常用命令： 

ros2 topic list
ros2 topic info /scan
ros2 topic echo /scan
ros2 topic hz /scan

ros2 topic list 用于查看话题列表。 ros2 topic info 用于查看话题类型和发布订阅关系。 ros2 topic echo 用于查看实时消息内容。 ros2 topic hz 用于查看消息发布频率。

服务 Service

Service 是 ROS 2 中基于请求和响应模型的通信机制。 

Client
   │
   │ Request
   ↓
Server
   │
   │ Response
   ↓
Client

Client 发送请求，Server 处理请求并返回结果。

Service 适合一次性、短时间完成、需要明确返回结果的操作。

典型场景包括： 重置设备、保存地图、切换模式、获取一次状态、打开或关闭某项功能。

例如： 

/reset_odometry
/save_map
/set_mode

如果任务执行时间较长，并且需要进度反馈或取消能力，通常不应使用普通 Service，而应使用 Action。

常用命令： 

ros2 service list
ros2 service type /service_name
ros2 service call /service_name interface_type "{}"

动作 Action

Action 用于执行需要一定时间完成的任务。

Action 主要包含 Goal、Feedback 和 Result 三部分。 

Goal
---
Result
---
Feedback

Goal 表示任务目标。 Feedback 表示任务执行过程中的状态反馈。 Result 表示任务最终执行结果。

Action 通常还支持取消任务。

典型使用场景包括： 机器人导航、机械臂轨迹执行、自动泊车、长时间运动任务。

例如导航任务中： 

Goal:
目标位置

Feedback:
当前位置
剩余距离
任务状态

Result:
成功
失败
取消

Nav2 中的 NavigateToPose 就是典型 Action。

常用命令： 

ros2 action list
ros2 action info /action_name

参数 Parameter

Parameter 用于保存节点运行时的配置数据。

参数属于具体节点，不是整个 ROS 2 系统共享的全局变量。

常见参数包括： 

max_speed
controller_frequency
frame_id
sensor_range
use_sim_time

参数可以避免将大量配置写死在代码中。

同一套程序可以通过不同参数适配不同机器人、不同硬件和不同运行环境。

常见 YAML 参数文件： 

controller:
  ros__parameters:
    max_speed: 0.5
    frequency: 20.0

ros__parameters 下的内容表示该节点的参数。

常用命令： 

ros2 param list
ros2 param get /controller max_speed
ros2 param set /controller max_speed 0.8

在支持动态参数修改的节点中，可以在运行过程中调整参数而不修改源码。

通信接口 Interface

通信接口用于定义 ROS 2 节点之间交换的数据结构。

主要包括 Message、Service 和 Action 三种接口。

Message

Message 使用 .msg 定义，主要用于 Topic。

例如机器人速度控制常使用： 

geometry_msgs/msg/Twist

其中包含线速度 linear 和角速度 angular。

Service Interface

Service 使用 .srv 定义。

结构分为 Request 和 Response： 

请求字段
---
返回字段

Action Interface

Action 使用 .action 定义。

结构分为 Goal、Result 和 Feedback： 

Goal
---
Result
---
Feedback

查看接口结构可以使用： 

ros2 interface show geometry_msgs/msg/Twist

阅读陌生项目时，可以先通过 Topic 类型找到 Interface，再根据 Interface 判断数据中包含哪些字段。

分布式通信

ROS 2 支持节点运行在不同计算机上。

只要网络配置和 ROS 2 通信配置正确，不同主机上的节点可以自动发现并进行 Topic、Service 和 Action 通信。

例如： 

机器人主机
├── lidar_node
├── camera_node
└── base_node

开发电脑
├── RViz
├── localization_node
└── debugging tools

机器人主机发布的 /scan 可以被开发电脑上的 RViz 或定位节点订阅。

ROS 2 的分布式通信通常不要求应用节点直接配置对方 IP 地址。

节点发现和底层通信主要由 DDS 等机制完成。

ROS_DOMAIN_ID 用于划分不同 ROS 2 通信域。 

export ROS_DOMAIN_ID=10

不同 ROS_DOMAIN_ID 的系统通常不会自动互相发现。

在实验室、多机器人和多人开发环境中，经常使用 ROS_DOMAIN_ID 隔离不同 ROS 2 系统。

DDS

DDS 全称 Data Distribution Service，是 ROS 2 底层通信的重要基础。

DDS 主要负责节点发现、数据分发、网络传输和 QoS 等能力。

ROS 2 通信结构可以简化为： 

Node
 ↓
rclcpp / rclpy
 ↓
ROS 2 Client Library
 ↓
RMW
 ↓
DDS
 ↓
Network

应用开发通常不需要直接使用 DDS API，而是通过 ROS 2 提供的 Publisher、Subscriber、Service 和 Action 接口使用底层通信能力。

QoS

QoS 用于定义 ROS 2 数据传输策略。

常见 QoS 配置包括 Reliability、History、Depth 和 Durability。

Reliability

Reliable 表示尽可能保证消息成功到达。

Best Effort 表示尽力传输，允许消息丢失。

高频传感器数据经常使用 Best Effort，因为旧数据价值较低，新数据会持续到达。

Depth

Depth 表示消息队列能够保存的消息数量。

例如： 

depth = 10

表示最多缓存一定数量的未处理消息，避免消息无限积压。

Durability

Volatile 表示新加入的 Subscriber 只接收之后发布的数据。

Transient Local 可以让新加入的 Subscriber 获取 Publisher 保存的部分历史数据。

如果 Topic 已经存在，但是 Subscriber 无法收到数据，应检查 Topic 名称、消息类型和 QoS 是否兼容。

Launch

Launch 用于统一启动和配置多个 ROS 2 节点。

一个 Launch 文件可以负责：

启动节点、设置节点名称、设置 Namespace、加载参数文件、进行 Topic Remapping、启动其他 Launch 文件以及设置环境参数。

典型启动方式： 

ros2 launch robot_bringup robot.launch.py

阅读 Launch 文件中的 Node 配置时，应重点关注： 

package
executable
name
namespace
parameters
remappings

package 表示功能包。 executable 表示需要启动的程序。 name 表示节点运行时名称。 parameters 表示需要加载的参数。 remappings 表示接口名称映射。

例如 Remapping 可以将节点默认使用的： 

/cmd_vel

映射成： 

/robot1/cmd_vel

这样可以在不修改节点源码的情况下修改通信连接关系。

TF

TF 用于管理 ROS 2 系统中不同坐标系之间的位置和姿态变换。

机器人系统中的传感器、底盘、地图和机械结构通常拥有不同坐标系。

典型移动机器人 TF 结构： 

map
 ↓
odom
 ↓
base_link
 ├── laser_link
 ├── camera_link
 └── imu_link

base_link

base_link 通常表示机器人主体的基准坐标系。

odom

odom 表示里程计坐标系。

odom 通常具有运动连续、短时间平滑的特点，但会随着时间产生累计漂移。

map

map 表示全局地图坐标系。

定位或 SLAM 系统通常负责计算 map 和 odom 之间的关系，用于修正长期定位误差。

移动机器人中常见关系： 

map → odom → base_link

TF 分为动态 TF 和静态 TF。

例如 odom 到 base_link 会随着机器人运动持续变化，属于动态 TF。

base_link 到 laser_link 由传感器固定安装位置决定，通常属于静态 TF。

常见 TF Topic： 

/tf
/tf_static

调试两个坐标系之间的变换： 

ros2 run tf2_ros tf2_echo map base_link

涉及位置、姿态、点云、导航目标等数据时，应同时确认数据所属的 frame。

URDF

URDF 全称 Unified Robot Description Format，用于描述机器人机械结构。

URDF 可以描述： 机器人包含哪些部件、部件尺寸、部件之间的连接关系、关节类型、碰撞模型、视觉模型、质量和惯性等信息。

URDF 最核心的两个概念是 Link 和 Joint。

Link

Link 表示机器人中的刚性部件。

例如： 

base_link
left_wheel_link
right_wheel_link
laser_link
camera_link
arm_link

Joint

Joint 表示两个 Link 之间的连接关系。

常见 Joint 类型包括固定关节、旋转关节和直线移动关节。

例如： 

base_link
    │
 fixed joint
    │
laser_link

表示激光雷达固定安装在机器人主体上。

URDF 通常和 robot_state_publisher 配合使用： 

URDF
 ↓
robot_state_publisher
 ↓
TF

robot_state_publisher 根据 URDF 中的机器人结构和关节状态发布对应 TF。

实际项目通常使用 Xacro 编写机器人描述。

Xacro 支持变量、宏、条件和文件复用，可以降低复杂 URDF 的维护成本。

Gazebo

Gazebo 是机器人仿真环境，用于模拟机器人、传感器和物理世界。

Gazebo 可以模拟： 重力、碰撞、摩擦、关节运动、机器人底盘、摄像头、激光雷达、IMU 等。

仿真机器人可以通过 ROS 2 接口发布和接收数据。

例如虚拟激光雷达可以发布： 

/scan

导航节点可以发布： 

/cmd_vel

仿真底盘接收 /cmd_vel 后根据物理模型运动。

如果仿真系统和真实机器人使用相同的 Topic 名称和消息类型，上层算法通常可以在真实环境和仿真环境之间复用。

仿真时间

Gazebo 可以暂停、加速和减速，因此仿真环境通常使用模拟时间。

Gazebo 可以发布： 

/clock

ROS 2 节点设置： 

use_sim_time = true

之后节点将使用仿真时间，而不是计算机系统时间。

RViz

RViz 是 ROS 2 的数据可视化工具。

RViz 不负责物理仿真，主要负责显示 ROS 2 系统中的数据。

常见可视化内容包括： 

LaserScan
PointCloud2
Image
Map
Path
Odometry
TF
RobotModel
Marker

在 SLAM 和导航项目中，RViz 常用于显示地图、机器人位置、激光雷达、全局路径、局部路径和导航目标。

Fixed Frame

Fixed Frame 是 RViz 中非常重要的配置。

它表示所有数据显示时使用的全局参考坐标系。

导航项目中通常设置为： 

map

如果某个数据所在坐标系无法通过 TF 转换到 Fixed Frame，RViz 就无法正确显示该数据。

因此 RViz 也常用于检查 TF 是否完整。

rqt

rqt 是 ROS 2 的图形化调试工具框架，包含多个插件。

rqt_graph

rqt_graph 用于显示节点与 Topic 之间的通信关系。 

lidar_node
    │
  /scan
    ↓
slam_node
    │
   /map
    ↓
navigation_node

它适合分析大型 ROS 2 系统的数据流和节点连接关系。

rqt_plot

rqt_plot 用于将某些 Topic 中的数值数据随时间绘制成曲线。

典型用途包括观察速度、传感器数据、控制误差和 PID 调试数据。

rqt_console

rqt_console 用于集中查看多个 ROS 2 节点输出的日志。

在多节点系统中，可以通过日志级别和节点名称过滤信息。

ROS 2 核心概念之间的关系

Workspace
   │
   └── Package
          │
          └── Node
                │
                ├── Topic
                ├── Service
                ├── Action
                └── Parameter

Topic / Service / Action
          │
          ↓
       Interface
          │
          ↓
         RMW
          │
          ↓
         DDS
          │
          ↓
        Network

工作空间负责管理整个项目。 功能包负责组织代码和资源。 节点负责运行具体功能。 Topic、Service 和 Action 负责节点之间通信。 Parameter 负责节点配置。 Interface 负责定义通信数据格式。 DDS 负责底层数据分发和网络通信。

机器人模型和坐标系统之间的主要关系： 

URDF
 ↓
robot_state_publisher
 ↓
TF
 ↓
RViz

URDF 负责描述机器人结构。 robot_state_publisher 根据机器人模型生成 TF。 TF 负责维护坐标系关系。 RViz 根据 TF 将机器人模型和其他 ROS 数据显示在统一坐标系中。

实际项目中的典型数据流

移动机器人导航系统中常见的数据流如下： 

LiDAR
 ↓
lidar_node
 ↓
/scan
 ↓
SLAM / Localization
 ↓
地图与机器人位置
 ↓
Navigation
 ↓
/cmd_vel
 ↓
base_node
 ↓
机器人运动
 ↓
/odom
 ↓
Localization

其中：

激光雷达节点通过 Topic 发布 /scan。

定位节点订阅 /scan 和 /odom，计算机器人位姿。

导航节点通过 Action 接收导航目标。

导航控制器通过 /cmd_vel 发布速度指令。

底盘节点订阅 /cmd_vel 并驱动机器人运动，同时发布 /odom。

URDF 描述机器人结构。

TF 维护 map、odom、base_link、laser_link 等坐标系关系。

Parameter 配置速度、控制频率、安全距离等运行参数。

Launch 统一启动机器人相关节点和参数。

Gazebo 用于仿真。

RViz 用于可视化。

rqt 用于分析节点和数据流。

阅读 ROS 2 项目的重点

阅读一个陌生节点时，应优先查找以下内容。

create_publisher：判断节点向外输出哪些数据。

create_subscription：判断节点需要哪些输入数据。

create_service：判断节点对外提供哪些请求接口。

create_client：判断节点调用哪些外部服务。

ActionServer：判断节点负责执行哪些长时间任务。

ActionClient：判断节点会向哪些模块发送任务。

declare_parameter：判断节点有哪些可配置参数。

create_timer：判断节点有哪些周期性任务。

推荐结合以下命令分析系统： 

ros2 node list
ros2 node info /node_name
ros2 topic list
ros2 topic info /topic_name
ros2 topic echo /topic_name
ros2 service list
ros2 action list
ros2 param list
ros2 interface show interface_type
rqt_graph

分析 ROS 2 项目时，重点应放在节点职责、数据流、通信接口、参数配置和 TF 坐标关系上。
